## Project layout

```
cmd/dun/                main package — cobra root + version/login/logout/keys/account
internal/api/           hand-rolled wrapper around the ogen client (Phase 1)
internal/api/gen/       ogen-generated, COMMITTED, regenerated by `make generate`
internal/auth/          ~/.dun/credentials store + FileProvider api.TokenProvider (Phase 2)

internal/tui/theme/     Lipgloss palette resolved once at process start
```

Each ring depends only on the rings inside it; see
[README.md](README.md) "The layers, from outside-in" for the

verbs register themselves via `init()` and the shell finds them via

## The `cmd/dun` entrypoint

`cmd/dun/main.go` defines the cobra root and three classes of
subcommand:

1. **The bare `dun`** — `RunE` calls `enterShell`, which loads the
   session and hands off to `shell.Run`. This is the primary
   interface. There is no `dun servers list`-style one-shot for game
   actions — see [CLAUDE.md](../../CLAUDE.md) "Interaction model".
2. **Operational subcommands** — `login`, `logout`, `keys`,
   `account`, `version`. These make sense _outside_ an authenticated
   session or have a one-shot shape that doesn't fit the prompt.
3. **`version` / `completion`** — side-effect-free and skip the
   logger initialization.

[cmd/dun/main.go](../../cmd/dun/main.go) at a glance:

- `PersistentFlags().StringVar(&logLevel, "log-level", ...)` is the
  one global flag.
- `PersistentPreRunE` opens the log file and installs the slog default;
  `PersistentPostRunE` closes it.
- `enterShell` is the shared entrypoint for both the bare `dun`
  invocation and the post-login handoff (see
  [cmd/dun/login.go](../../cmd/dun/login.go)). Missing credentials
  print `not logged in — run `dun login`` and exit non-zero.

The version string is `const Version = "0.0.0-dev"` in
[cmd/dun/main.go](../../cmd/dun/main.go#L27); release builds override
it via `-ldflags` (Phase 14).

## `loadSession` — the per-command bundle

Every cobra subcommand (and the bare-`dun` shell entry) starts with
`loadSession()` ([cmd/dun/client.go](../../cmd/dun/client.go)):

```go
type session struct {
    cfg    *config.Config
    store  *auth.Store
    client *api.Client
}
```

It reads `~/.dun/config.toml` + `~/.dun/credentials` and builds an
`*api.Client` configured for the active base URL. The client uses an
`auth.FileProvider` rather than a captured token, so any in-process
mutation of `store.Current` (e.g. a successful `dun login`) is picked
up on the next API call without rebuilding the client.

That detail matters for the post-login handoff: `runLogin` mutates the
store, then immediately calls `enterShell`, which calls `loadSession`
again. The second `loadSession` gets the fresh credential because both
calls go through the same on-disk file — see
[03-auth-and-config.md](03-auth-and-config.md).

## Storage layout (`~/.dun/`)

All persistent client state lives under a single dotfolder in the
user's home — in the spirit of `~/.aws/`, `~/.ssh/`, `~/.kube/`.

```
~/.dun/
├── config.toml      # defaults (base URL, …)
├── credentials      # API keys, TOML, mode 0600
├── history          # REPL line history (managed by readline)
├── state.json       # last-used (server, world, kingdom) scope
└── dun-cli.log      # JSON slog output, append-mode
```

Rules ([CLAUDE.md](../../CLAUDE.md) "Storage layout"):

- **Strict `~/.dun/`.** No XDG env var support; no `$DUN_HOME`
  override. Tests isolate via `t.Setenv("HOME", tempDir)`.
- **Directory mode 0700**, created lazily on first write by whichever
  package needs a file there.
- **File modes**: default 0644; `credentials` is 0600.
- **No OS keychain.** `zalando/go-keyring` is not a dependency.

Every package that writes under `~/.dun/` does its own
`os.MkdirAll(dir, 0o700)` and atomic write+rename. There is no shared
"open the dotfolder" helper because the only thing the packages share
is the path — see the per-file owners table below.

| File | Owner package | Mode | Format |
|---|---|---|---|
| `config.toml` | [internal/config](../../internal/config/config.go) | 0644 | TOML, viper |
| `credentials` | [internal/auth](../../internal/auth/store.go) | 0600 | TOML, pelletier/go-toml |
| `history` | [internal/tui/shell](../../internal/tui/shell/shell.go) | 0644 | plain text, readline |
| `state.json` | [internal/tui/shell](../../internal/tui/shell/state.go) | 0644 | JSON |
| `dun-cli.log` | [internal/log](../../internal/log/log.go) | 0644 | JSON, append-mode |

## Build commands

```
make generate   # regenerate internal/api/gen/* from docs/backend/openapi.yaml
make build      # compile bin/dun
make test       # go test ./...
make lint       # golangci-lint run
make run        # go run ./cmd/dun tui (TUI from source)
make tidy       # go mod tidy
make clean      # remove bin/
make help       # list targets
```

[Makefile](../../Makefile) is short — every recipe is one line. The
codegen target reads [ogen.yml](../../ogen.yml) (which disables ogen's
unused server-side features) and writes the package
`internal/api/gen/`. Lint config lives at
[.golangci.yml](../../.golangci.yml); the generated package is
exempted from every linter.

The `make run` target is a leftover from Phase 0 that launches `go run
./cmd/dun tui` — Phase 3 replaced the `tui` subcommand with a bare
`dun` shell. Running `go run ./cmd/dun` directly is the supported path
today.

## Backend contract — IMPORTANT

`docs/backend/` is a **mirror** of the upstream backend repo
(github.com/fguillen/dun). It is overwritten by
[scripts/sync-backend-docs.sh](../../scripts/sync-backend-docs.sh) on
every sync.

- **Never hand-edit any file under `docs/backend/`** — your change will
  vanish on the next sync.
- When the backend spec changes:
  ```
  ./scripts/sync-backend-docs.sh && make generate
  ```
- When in doubt about HTTP behavior, prefer
  [docs/backend/openapi.yaml](../backend/openapi.yaml).
- When in doubt about game rules, prefer
  [docs/backend/game-design.md](../backend/game-design.md) (section
  refs like `§17.1` point there).
- A flat endpoint index lives at
  [docs/backend/api-endpoints.md](../backend/api-endpoints.md).

Likewise, **never hand-edit any file under `internal/api/gen/`** —
both directories are generated. The lint config excludes the generated
package from every linter so a tweak there isn't accidentally
preserved.

## Logging

[internal/log/log.go](../../internal/log/log.go) opens
`~/.dun/dun-cli.log` in append mode and returns a `*slog.Logger` plus
the underlying `io.Closer`. `cmd/dun/main.go` installs it as the
default and closes it in `PersistentPostRunE`.

Conventions ([CLAUDE.md](../../CLAUDE.md) "Conventions"):

- Every package uses `slog.Default()`; never write to stdout / stderr
  from TUI code (the alt-screen used by selectors swallows it, and the
  REPL's scrollback would mix log lines with user output).
- The api wrapper logs each request with `slog.String("request_id",
  ...)` so a misbehaving backend response is one `grep
  "request_id"` away from a trace.
- Level is `info` by default; `--log-level debug` flips on the
  per-request "api ok" line emitted by `internal/api`.

The level parser accepts `debug | info | warn | error`,
case-insensitive; anything else falls back to `info`.

## Tests

- **Framework**: `testing` + `testify/require` + `testify/assert`.
- **Table-driven** is the default; `_test.go` lives next to the file
  under test.
- **TUI tests** use `charmbracelet/x/exp/teatest` for golden snapshots
  of `tea.Model` output.
- **HTTP tests** in `internal/api/` use `httptest.Server` to stub the
  backend — never a mock. The wrapper is the boundary, so its tests
  exercise real HTTP round-trips against a local server.
- **Filesystem isolation** is via `t.Setenv("HOME", tempDir)` per
  the storage-layout rule; no test ever touches the developer's real
  `~/.dun/`.

The full suite runs via `make test`. The cobra `cmd/dun` tests stub
`stdin` / `stdout` to exercise the magic-link prompts without an
actual terminal.

## What to do when adding a new verb

1. Decide the phase from [TODO.md](../../TODO.md) — verbs should ship
   in roadmap order so each phase builds on the previous.
2. Add a new file under [internal/tui/verbs/](../../internal/tui/verbs/),
   call `shell.Register` from `init()`. See
   [05-verbs.md](05-verbs.md) for the file template.
3. Add wrapper method(s) to [internal/api/client.go](../../internal/api/client.go)
   for any operation the verb calls. See
   [02-api-client.md](02-api-client.md) for the `call()` pattern.
4. Add tests next to each file. Verbs are tested by stubbing the
   `*api.Client` via the same `httptest.Server` pattern; the shell
   dispatcher itself has table-driven Parse tests.
5. Update [docs/tutorial.md](../tutorial.md) **in the same commit** —
   it documents only what's actually implemented. The
   [CLAUDE.md](../../CLAUDE.md) "Conventions" section is firm on this.
6. Update [commands-reference.md](commands-reference.md) so the new
   verb is cross-linked to its `operationId`.
